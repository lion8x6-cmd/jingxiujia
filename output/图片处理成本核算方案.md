# 精修家 · 图片处理成本核算方案

> 豆包 Seedream 5.0 Pro 云 API vs 开源自托管模型
> 核算日期：2026-08-12
> 适用阶段：初期项目团队（0-6 个月）

---

## 一、两种方案概述

### 方案 A：豆包云 API（当前方案）

小程序直接调用火山方舟方舟平台的 Doubao-Seedream-5.0-pro 模型，按张付费，无需服务器和 GPU。

- **接口**：`POST https://ark.cn-beijing.volces.com/api/v3/images/generations`
- **模型**：`doubao-seedream-5-0-pro-260628`
- **优势**：零运维、无限并发、商用级画质、接入即用
- **劣势**：按张付费，数据走字节服务器

### 方案 B：自托管开源模型

在自有/租赁 GPU 服务器上部署开源图像编辑模型（Qwen-Image-Edit / Kolors / FLUX 等），小程序通过自建后端中转调用。

- **硬件**：NVIDIA RTX 4090 24GB 或同级 GPU
- **优势**：单张成本随规模摊薄、数据自主可控、可微调专属模型
- **劣势**：固定月费、需运维、画质需工程拼接才能接近商用级

### 3.2 盈亏平衡点

```
盈亏平衡点 ≈ 月固定成本 ÷ 单张变动成本差
           ≈ ¥2,000 ÷ ¥0.30
           ≈ 6,700 张/月（约日均 220 张）
```

**当月出图量低于 6,700 张时，豆包 API 更划算；超过后，自托管开始显现成本优势。**

## 五、初期项目建议

### ✅ 推荐方案：继续使用豆包 API

理由如下：

1. **成本结构匹配初期不确定性**
   自托管 ¥2,000/月是固定沉没成本，不管产品有没有人用都要付；豆包是变动成本，没人用就是 ¥0。MVP 阶段用户量无法预测，避免固定烧钱。

2. **盈亏平衡点过高**
   要月均 6,700 张以上才划算，相当于**日均 220 次精修请求**。初期产品大概率摸不到这个量级，强行自托管等于每月白扔 ¥2,000。

3. **画质直接影响付费转化**
   豆包 5.0 Pro 是目前国内商用顶级模型，在人像自然度、皮肤质感、光影处理上明显优于开源模型。初期产品效果决定用户是否愿意付费，**省几毛钱可能损失几十块客单价**。

4. **专注核心业务**
   初期团队人力宝贵，自托管需要写后端中转、部署模型、处理 GPU 故障、监控排队情况，至少 5-10 人天工作量，不如投入到产品体验和用户增长上。

### 💡 立即可以做的优化

**把输出分辨率从 2K 降到标准分辨率**

当前代码配置：

```js
// utils/ark-config.js
size: '2K'  // 当前：¥0.60/张
```

改为：

```js
size: '1K'  // 或标准分辨率：¥0.30/张
```

- 标准分辨率上限 236 万像素（约 1536×1536），手机端全屏展示完全够用
- 成本**直接减半**，用户肉眼几乎无差异
- 月出图 5,000 张时，月费从 ¥3,000 降到 ¥1,500

## 六、长期演进路线

```
阶段 1：MVP 验证期（0-3 个月）
├── 方案：豆包 API 标准分辨率（¥0.30/张）
├── 预计月成本：¥0-1,500
└── 重点：验证产品价值和付费意愿

阶段 2：增长期（3-6 个月）
├── 方案：豆包 API 为主，2K 分辨率可选（会员权益）
├── 预计月成本：¥1,500-5,000
└── 重点：积累用户、打磨体验、收集数据

阶段 3：规模期（6 个月+，月出图 >10,000 张）
├── 方案：混合架构
│   ├── 80% 请求 → 自托管 Qwen-Image-Edit/Kolors（RTX 4090 ×2）
│   └── 20% 高质量/复杂请求 → 豆包 API 兜底
├── 预计月成本：¥2,000-2,500（对比纯豆包 ¥3,000+）
└── 重点：成本优化、模型微调、专属风格训练

阶段 4：成熟期（月出图 >50,000 张）
├── 方案：多卡集群 + 自研微调模型 + CDN 分发
├── 预计月成本：¥5,000-8,000（对比纯豆包 ¥15,000+）
└── 重点：规模化降本、数据飞轮、技术壁垒
```

## 七、混合架构参考设计

当进入阶段 3 时，建议在小程序和模型之间加一层**后端路由服务**：

```
小程序请求
    │
    ▼
┌─────────────────────────────┐
│      后端路由层（Node.js）    │
│  ┌───────────────────────┐  │
│  │ 1. 鉴权 & 计费统计     │  │
│  │ 2. 请求内容安全审核    │  │
│  │ 3. 智能路由判断：      │  │
│  │    • 普通请求 → 自托管 │  │
│  │    • 复杂请求 → 豆包   │  │
│  │ 4. 失败自动降级        │  │
│  │ 5. 结果缓存（重复请求）│  │
│  └───────────────────────┘  │
└──────────┬──────────────────┘
           │
     ┌─────┴─────┐
     ▼           ▼
┌─────────┐ ┌──────────────┐
│ 自托管   │ │ 豆包 API     │
│ RTX4090 │ │ ¥0.30/张兜底 │
│ ¥2000/月│ │              │
└─────────┘ └──────────────┘
```

**额外收益**：即使现阶段不部署自托管，这层后端也应该尽快加上——目前 API Key 直接打包在小程序前端，存在被反编译泄露的风险。

## 八、结论

| 场景 | 推荐方案 |
|---|---|
| **当前 MVP 阶段** | 🟢 豆包 API 标准分辨率（¥0.30/张） |
| 月出图 < 6,000 张 | 🟢 豆包 API |
| 月出图 6,000-10,000 张 | 🟡 豆包 API（运维省心优先） |
| 月出图 > 10,000 张且已验证 PMF | 🔵 混合架构（自托管为主 + 豆包兜底） |
| 有严格数据合规要求 | 🔵 自托管（私有化部署） |

> **核心原则：初期不要为了省不确定的钱，投入确定的开发和运维成本。等账单真的疼了，再优化不迟。**
